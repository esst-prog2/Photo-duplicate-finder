## Problem Statement
The project has a README and a lot of checkable engineering behind it, but nothing that introduces it to a reader in one pass. The readers are classmates and the teacher. They should see in under a minute what the tool does, that it works, and where it stops. The thing it replaces is sorting a photo folder by hand.

## What Makes This Cool
The moment is the result: point the tool at a folder of photos and get an Excel file with one table per group of look-alikes, the best copy highlighted in each. Against sorting by hand, the tool compares what the pictures look like, not their names, and shows every group in one report. What sets the page apart from a feature list is that the work behind it can be checked: a planted benchmark, tests that fail on purpose, a mutation test and a process log.

## Constraints
- Content only: plain text in the repo. Layout and hosting come later.
- Only facts already verified in the repo. No new claims.
- The page must say what the tool misses.
- No exact counts promised: how many groups a folder gives depends on the photos and the threshold, so the page never says how many photos go in or how many groups come out.
- Audience: classmates and the teacher.

## Premises
All four agreed.
1. The deliverable is the content of the page (headline, one-line promise, how it works, proof, honest limits, how to try it), as plain text in the repo. Layout and hosting come later.
2. The page states what the tool misses (mirrored, turned, bordered or heavily cropped photos), because readers can test that in a minute and an overclaim would be the first thing they find.
3. The page uses only facts already verified in the repo. No new claims.
4. The page lives as a file in the repo for now. Publishing it is not needed to finish the content.

## Approaches Considered
### Approach A: One-screen pitch
Not chosen: shows the result but none of the proof, so the teacher sees what it does and not how well it was built.
### Approach B: Result first, proof second (chosen)
See below.
### Approach C: Try to fool it
Not chosen as the whole page: memorable and honest, but narrow, and its table rests on two measured photos. The limits table is reused inside B.

## Recommended Approach
B, result first, proof second. The audience includes a teacher, the engineering behind the project is its real strength, and the result still opens the page.

Page outline:
1. Headline and one-line promise.
2. The result: a folder of photos in, an Excel report out, one table per group of look-alikes with the best copy highlighted. No promised counts.
3. How it works in four steps: read the folder, compare what each photo looks like, group photos that look alike, write one table per group with the file to keep highlighted.
4. Proof: the planted benchmark, a test that goes red on purpose and then green, the mutation test.
5. Honest limits: what it catches and what it misses.
6. Try it: the setup and the one command.
7. How it was built: the spec, the planning log, the process log.

Where each claim comes from. Every number on the page must trace to one of these:

| Claim | Source |
|---|---|
| A folder goes in; one table per group of look-alikes comes out, the best copy highlighted (no counts promised) | README section 1; `tests/test_report.py`, `tests/test_cli.py` |
| On the project's own planted test set, the tool found every planted group and no group mixed unrelated photos (a test result, not a promise for other folders) | `tests/test_benchmark.py`; `PLANNING_LOG.md` 2026-10-09 |
| The test goes red when one setting is wrong and green when it is fixed | `PLANNING_LOG.md` 2026-10-09 (one setting changed on purpose made every photo land in a single group) |
| Almost every deliberate code change was caught by the tests; the few that were not cannot change what the program does | commit `4331ca0`; `PLANNING_LOG.md` 2026-11-06 |
| Reads .jpg, .jpeg and .png; warns about skipped .heic and similar | README section 1; `tests/test_scanner.py`, `tests/test_cli.py` |
| Catches resizing, re-saving and brightness changes; misses mirroring, turning, borders and large crops | measured by hand on two photos on 2026-11-13, NOT yet saved in the repo (see Open Questions) |

## Open Questions
1. The catches-and-misses table was measured in a chat session on two photos and not saved. It needs a small repeatable script or a log entry before the page cites it.
2. The benchmark photos are the owner's own, in a public repo. Decide whether any of them appear on the page.
3. A burst of different shots of one scene was never tested, so the page must not claim it.
4. The summary line counts a group that mixes an exact copy and a similar copy in both numbers (README section 1 explains this). Decide whether the page quotes that line or avoids it.
5. File name and place for the page content, for example `docs/promo-page.md`.
6. Numbers: decided by the user: test results may stay on the page, stated in words and scoped to the test set. No count of photos or groups is promised for a reader's folder.

## Success Criteria
- A classmate can say, in their own words, what the tool does and what it cannot do.
- Every number on the page traces to a test, a commit or a log entry.
- Nothing on the page fails when a reader tries it (a mirrored photo, a photo turned 90 degrees).
- The page promises no exact count of photos or groups.

## Distribution Plan
A Markdown file in the repo, readable on GitHub. Publishing it as a site (for example with GitHub Pages) is a later step. No pipeline is needed for the content.
